01

Executive Summary

A closed-loop release system for industrial automation.

I designed, built, validated, and owned a platform that connected approved source code to deployment targets and returned verified installed state to the same operational record.

Before the platform, version visibility was inconsistent and rollout was tedious and expert-dependent. The solution joined an Angular operations interface, C#/ASP.NET services, Git-versioned software, GMP qualification evidence, controlled SSH distribution, and OPC UA/MQTT state feedback. It supported more than 150 physical and virtual PLC targets, alongside target computers and multiple automation artefact types.

02

Context

Software releases were production changes, not simple file transfers.

The platform operated in a regulated manufacturing environment where an automation change had to connect a specific approved version with its intended targets, qualification evidence, release approval, deployment method, recovery path, and installed result.

The managed scope included PLC applications, reusable libraries, firmware and runtime versions, recipes, and supporting software packages across physical PLCs, virtual PLCs, and computers. Any useful solution therefore had to serve engineering, operations, release governance, and validation at the same time.

Design constraint

Make controlled release work easier without separating operational speed from GMP evidence and recovery readiness.

03

Problem

The release chain was fragmented and depended on expert memory.

Teams could not reliably answer a basic operational question from one place: Which approved software version is installed on this device right now?

01

Version ambiguity

Approved source, packaged release, intended target, and actual device state could drift apart.

02

Manual rollout

Deployment required repetitive operational steps and specialist knowledge for each change.

03

Scattered evidence

Qualification evidence, approvals, release notes, and rollback instructions were not one navigable release record.

04

Open-loop delivery

Sending software was not enough; the system needed device-reported version and runtime confirmation.

04

Solution

One system connected governance, delivery, and state feedback.

I modelled releases as operational records rather than loose files. Each record connected versioned software, target systems, validation evidence, approval state, deployment status, recovery information, and reported installed state.

05

My Involvement

I owned the system from pitch and domain model through validation and operation.

This was not a handoff or a one-off deployment script. I was the 0-to-1 builder and system owner, responsible for shaping the workflow, implementing the platform, producing qualification evidence, and making it operable in the manufacturing environment.

Discover + define

Created the low-fidelity concept and pitch, captured user requirements, and connected the design to risk assessment and regulated release needs.

Architect + model

Defined versions, target systems, release records, supporting evidence, deployment state, installed state, and recovery information as one domain.

Build full stack

Implemented the Angular operations interface and C#/ASP.NET services, plus the release and evidence workflows around them.

Automate deployment

Built the path that delivered approved software to PLC and computer targets over SSH, covering multiple release artefact types.

Close the loop

Integrated OPC UA/MQTT version and runtime feedback so installed device state returned to the dashboard.

Validate + own

Prepared IQ/OQ evidence, release records, and rollback-ready documentation, then owned the workflow as an operational system.

06

Outcome + Bottom-Line Impact

A repeatable release operation replaced fragmented manual coordination.

The business result was operational leverage: the same controlled workflow could prepare, approve, distribute, verify, and recover automation releases across a large heterogeneous fleet.

150+ Fleet reach

Controlled software distribution across physical and virtual PLC targets.

Less manual handling Engineering capacity

Automated repetitive delivery steps so specialists could focus on release decisions and exceptions.

Traceable Risk + audit readiness

Linked version, evidence, approval, target, deployment, rollback, and installed state.

Closed loop Operational confidence

Device-reported state made rollout results visible instead of assuming delivery meant success.

What changed for the bottom line

The platform lowered the labor and coordination cost of each controlled release, reduced dependency on individual expert memory, reduced the operational risk of version mismatch, and made the release process reusable across the fleet. No audited financial amount was available in the source material, so the impact is stated in operational terms rather than as an invented savings figure.

Evidence boundary

The architecture and interface are public-safe reconstructions of the system. Equipment names, release records, site data, and employer-specific identifiers are excluded or generalized.

Selected artefacts

Git-controlled automation software, release and target records, IQ/OQ and CSV evidence, release notes, rollback procedures, SSH deployment, and OPC UA/MQTT feedback.
